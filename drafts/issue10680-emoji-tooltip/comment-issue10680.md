Reproduced on current main and traced to a specific cause.

Observed: tooltip sticks after hovering a tile in the note icon picker and then typing in its search box, starting in 0.104.0, and survives everything short of a restart.

Reproduced on main (964e23ec56), web client on Linux, driven with Playwright: open a note, open the icon picker, hover a tile until its tooltip shows, type in the search box. The tooltip's trigger span leaves the DOM (`aria-describedby` back-reference resolves to nothing) while the popup stays a direct child of `body`, and it survives closing the picker and clicking elsewhere - the restart-requiring signature from the report.

Cause: the icon picker attaches one delegated Bootstrap tooltip to the grid container (`apps/client/src/widgets/react/IconPicker.tsx`, `useStaticTooltip(iconListRef, { selector: "span", ... })`; in 0.104.0 the same code was in `note_icon.tsx`). Bootstrap's delegated mode creates a per-span Tooltip instance that only hides on mouseleave of that same span, and appends the popup to `document.body`. Typing in the search re-renders the react-window grid, so the hovered span (keyed by icon id) is replaced; no mouseleave ever fires on a removed element, so the per-span instance never hides and its popup is orphaned in `document.body`. The unmount sweep in `hooks.tsx` walks `element.querySelectorAll("[aria-describedby]")`, which cannot see a trigger that already left the container, so closing the picker does not remove it either. Scrolling the virtualized grid while hovering triggers the same leak.

Why 0.104.0: up to v0.103.0 the `useStaticTooltip` cleanup ended with a blanket `document.querySelectorAll('.tooltip').forEach(t => t.remove())`, which wiped the orphan as soon as the picker closed. Commit 95b244e0c6 (first released in v0.104.0) replaced that with the scoped `[aria-describedby]` sweep, for good reasons, but that unmasked this leak. So the picker-close self-heal existed in 0.103.x and is gone in 0.104.x, which matches the report exactly.

Smallest fix: in `useStaticTooltip` (`apps/client/src/widgets/react/hooks.tsx`), for delegated (`selector:`) configs, track the delegate elements whose tooltips are showing (Bootstrap's `inserted.bs.tooltip` / `hidden.bs.tooltip` events bubble to the container) and add a MutationObserver on the container that calls `Tooltip.getInstance(target)?.dispose()` for any tracked trigger with `isConnected === false`. `dispose()` removes a currently shown popup, same property the fix for (10567) relies on, and the existing `Tooltip.prototype.dispose` patch already guards the bootstrap 37474 pending-callback crash. A regression test fits the existing delegated-remount pattern in `hooks.spec.tsx`.

Verified with: live repro above, code reading at main (964e23ec56; the implicated files are unchanged since 372a749ff2), `git show v0.103.0:.../note_icon.tsx` and `v0.104.0:.../note_icon.tsx`, `git show 95b244e0c6`, and Bootstrap 5.3 `tooltip.js` (delegated `getOrCreateInstance`, `container === false` resolving to `document.body`).

Remaining uncertainty: I could not watch the attached video, so I could not confirm it shows the note icon picker rather than the CKEditor toolbar emoji picker. The CKEditor picker's grid also detaches tiles on search without a mouseleave, but its TooltipManager self-heals on Escape, on focusing anything without a tooltip, and on the next `editor.ui` update, so it cannot explain a restart-requiring tooltip, and nothing on that path changed between 0.103.0 (ckeditor5 48.0.1) and 0.104.0 (48.2.0); `tooltipmanager.ts` and `emojigridview.ts` are identical between those CKEditor tags. The icon-picker leak above is confirmed regardless.
