## Why

Closes #8169

A backend script can call `api.createNewNote({ noteId: "0d8949e4-6fe3-4f4b-82c1-679baf64fccb", ... })`. The note is stored, but links to it fail silently, and no `internalLink` or `includeNoteLink` relation is created.

Root cause: `createNewNote()` in `packages/trilium-core/src/services/notes.ts` validates the parent, the content and the creation dates, but not `params.noteId`. The backend script API and the internal create-note route both go through this function. All link consumers assume `[A-Za-z0-9_]`: client `link.ts`, the `#root/...` pattern in `packages/commons`, and the server `findInternalLinks()`, wiki-link and include-note scanners. Only ETAPI checked the ID format.

## What

- New pure helper `isValidEntityId(id)` in `packages/trilium-core/src/services/utils/index.ts`, with the same pattern that ETAPI used (`/^[A-Za-z0-9_]{4,128}$/`).
- `createNewNote()` throws `ValidationError` (HTTP 400 on the internal route) when a forced `noteId` is not a string or does not match. A falsy `noteId` (`undefined`, `null`, `""`) still means "generate an ID", as before.
- The ETAPI `isValidEntityId` validator calls the core helper, so the tree has one copy of the pattern. Its behaviour and message are unchanged.
- `apps/script-deployer`: `codeNoteId()` and `renderNoteId()` replace each character outside `[A-Za-z0-9_]` with `_`. The in-tree script IDs are kebab-case (`auto-import-xopp`), so `_sd_auto-import-xopp` would now be rejected. This is a dev-only harness, thus new keys for its notes are harmless.

## Scope

- The `BNote` constructor is not changed. Becca load and sync construct `BNote` with legacy IDs.
- No repair of notes that exist with a non-conforming ID. They stay as they are, and links to them continue to fail.
- No ID normalisation in core and no check of `branchId`. The TODO about a forced ID that already exists is not touched.
- Behaviour change for user scripts: `api.createOrUpdateLauncher({ id })` builds `al_${id}`. An `id` with a dash now throws when the launcher does not exist yet. The JSDoc already says "only alphanumeric", so I did not add normalisation. Tell me if you prefer that.
- The in-tree callers in core and server that force a `noteId` (hidden subtree, task states, launchers, zip import, in-app help) use conforming IDs. Third-party scripts that force other IDs will now get an error.
- A textual conflict with the open PR 11434 is possible. It edits the date-validation block immediately above the new guard.
