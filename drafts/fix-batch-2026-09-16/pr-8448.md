## Why

A shared note with the documented `#shareExternalLink="https://..."` label does not act as an external link in the share navigation tree. The tree shows a normal internal `./<shareId>` link with no `target` or `rel`. The label help text ("Note will act as a link to an external website in the share tree.") and `Sharing.md` ("in the shared navigation or in an index") promise an external link there.

Root cause: `packages/share-theme/src/templates/tree_item.ejs` read only the older `shareExternal` label (`note.hasLabel("shareExternal")`), while the docs and `content_renderer.ts` use `shareExternalLink`.

A second defect hit the exact setup from the issue thread (`#shareExternalLink="https://github.com" #shareExternal`). The Subpages list in `page.ejs` used `getLabelValue("shareExternal") ?? getLabelValue("shareExternalLink")`. A `#shareExternal` label with no value returns `""`, which is not nullish, so the URL was dropped and `sanitizeUrl("")` gave `about:blank`. The tree did the same.

Closes #8448

## What

- `tree_item.ejs` and the Subpages list in `page.ejs` now use the first non-empty value of `shareExternalLink`, then `shareExternal`. A note is external only when a URL is present.
- A label with no URL renders as a normal internal link, not as `about:blank`.
- Behavior change: when the two labels hold different URLs, `shareExternalLink` now wins. Before, the Subpages list preferred `shareExternal` and the tree read only `shareExternal`. The new order agrees with `content_renderer.ts`, which reads only `shareExternalLink`.
- New cases in `apps/server/src/share/content_renderer.spec.ts`. No new dependency, no docs change.
