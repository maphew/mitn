## Why

A display name (alias) with a comma breaks a label or relation definition. In the attribute detail dialog, the alias `myLabel, very pretty` is saved, but it shows as `myLabel` after the dialog is opened again. When the text after the comma is a valid token, the token is applied. I ran the `upstream/main` parser on the strings that `serialize()` writes: the alias `Foo, promoted` makes a definition promoted, `Pick, options=x` adds a select option, `Amount, precision=2` sets a precision, and `Parent, inverse=x` sets an inverse relation. `Size, number` does not change the type there, because `serialize()` writes the type after the alias and the last token wins. It does change the type in a hand-typed definition that has the alias last (`promoted,single,text,alias=Size, number` reads as type `number`).

Root cause: a definition is stored as comma-separated tokens. In `packages/commons/src/lib/promoted_attribute_definition_parser.ts`, `parse()` does `value.split(",")` before it looks at any token, and `serialize()` wrote the alias raw (`alias=${definition.promotedAlias}`). Thus `promoted,alias=myLabel, very pretty,single,text` is read as the alias `myLabel` plus a stray token `very pretty`. The dialog (`attribute_detail.tsx`, alias `FormTextBox` to `commitDefinition()` to `serialize()`) does no validation.

Closes #6853

## What

- `serialize()` writes the alias through a new private `encodeAlias()`: `%` to `%25` first, then `,` to `%2C`.
- `parse()` reads the alias through `decodeAlias()`: `%2C` to `,`, then `%25` to `%` last. `alias` with no `=` still gives `undefined`.
- This is the same substitution that `encodeOption()`/`decodeOption()` already use for select options, for the same reason: all released parsers split on `,` first, so the quoted form that the issue suggests (`alias='a, b'`) would still be cut by them. `;` is not encoded, because it separates nothing in an alias.
- No caller changes. Each writer of a user-typed alias uses `serialize()` (`attribute_detail.tsx`, `services/attributes.ts`, the board API, migration 0240) and each reader uses `parse()`.

Trade-offs, the same ones already accepted for select options: (a) a stored alias that literally contains `%2C` or `%25` now reads as `,` or `%`; (b) a client that is not upgraded shows the escaped text (`My%2C Label`, `100%25`), but it writes the same string back, so the data is not lost and there is no write conflict between sync peers; (c) a script that reads the raw definition value sees the escaped alias, as it already does for options.

## Scope

- The ribbon attribute editor stores typed text as it is, so a hand-typed definition must use `%2C` for a comma in the alias. A raw comma there is still split. The issue names this path too, and this change does not add validation to it.
- `buildPromotedDefinition()` in `packages/trilium-core/src/services/import/collection_utils.ts` still replaces `,` and `=` in an imported column name with a space. It can use `serialize()` in a follow-up, but that changes the import output and its tests.
- `hidden_subtree.ts` and `hidden_subtree_templates.ts` write `alias=${t(...)}` raw. No shipped translation of those keys contains a comma now, so this is a latent risk and not a defect.
- `parse()` trims each token, so leading or trailing spaces in an alias are still lost. Select options have the same behavior.
- Docs: `Promoted Attributes.md` in the User Guide shows a hand-typed definition with `alias=Color` and does not mention an escape. Nothing on the page is now wrong. I did not add the `%2C` note, because the User Guide must be edited with `pnpm edit-docs:edit-docs`, and the select option escape is not documented either.
- `encodeAlias()` and `encodeOption()` are almost the same. I kept them apart so that the `;` difference stays visible.
