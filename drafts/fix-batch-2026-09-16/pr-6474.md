## Why

In a table collection, Tab from a cell that was changed moves to the next cell, but about one server round trip later the new editor closes, the caret disappears and focus falls to the document body. The next Tab starts again from the first column, and typed text can go into the wrong cell. Issue 10820 reports the same symptoms.

Closes #6474

Root cause: Tab is the native focus move between Tabulator cells. The blur commits cell A, `cellEdited` writes the title or attribute (`row_editing.ts`), and the editor of cell B opens in the same task. The write returns through `entitiesReloaded` in `data.tsx`, `useData` calls `refresh(false)`, and the data effect in `tabulator.tsx` calls `replaceData()` without conditions. `replaceData()` rebuilds every row, and Tabulator's EditModule cancels the open editor on its internal `data-refreshing` event.

## What

- `apps/client/src/widgets/collections/table/tabulator.tsx`: while a cell editor is mounted (the `tabulator-editing` class on the table element), the data effect keeps the latest rows in `pendingDataRef` and does not call `replaceData()`.
- A `cellEditCancelled` handler applies the held rows from a `setTimeout(..., 0)`, only if no editor is open when the timer runs. The delay is necessary because Tab ends one edit before the next editor opens in the same task.
- The effect cleanup clears the timer and the held rows before `tabulator.destroy()`.
- `cellEdited` does not apply the held rows. A committed edit always writes, and its reload delivers rows with the new value. The held snapshot would show the old value for a moment.

## Scope

- Native Shift+Tab does not move to the previous cell. The cell element is the previous focus stop of its own editor input, so Shift+Tab opens the same cell again. This needs the custom key handling that 10820 requests, and it is not part of this change.
- A custom editor (SelectEditor, ColorEditor, RelationEditor) that calls `success()` with a value that did not change fires neither `cellEdited` nor `cellEditCancelled`. Rows held at that moment stay held until the next reload or the next cancelled edit. The cells already show the local values, so I did not add a second trigger.
- While an editor is open, a row that another window adds or deletes shows only after the editor closes. A commit to a row that was deleted elsewhere then gets a server error.
- `setColumns()` is not guarded. An attribute definition change from sync or another window still closes an open editor. The table's own definition writes are already filtered by `componentId` in `data.tsx`. This behavior existed before this change.
- The second-window case was not exercised live, and I could not view the video in 6474. The mechanism is certain from the code, and the live run matches the report.
