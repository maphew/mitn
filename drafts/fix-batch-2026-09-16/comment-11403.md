Observed: the stack has no Trilium frames. It is fully inside CKEditor 5's "Powered by" badge (ckeditor5-ui `badge/badge.ts`): focus change -> `_showBalloon` -> `BalloonPanelView.pin/attachTo` -> the positioning function in `getLowerCornerPosition`.

Cause: that function does `visibleEditableElementRect.clone().moveTo(...).getIntersection(balloonRect.clone().moveTo(...))!` and then calls `.getVisible()` on the result. `Rect.getIntersection()` returns `null` when the computed width or height is negative. The non-null assertion hides that case, and the editor watchdog reports it as `unexpected-error`. Trilium uses the `GPL` license key, so the badge plugin is active. It is only hidden with CSS (`.ck-powered-by-balloon { display: none !important }`), so this positioning code still runs on each editor focus change. The code is the same in ckeditor5 48.4.0 (Trilium v0.105.0), in 48.5.0 (current main), and on CKEditor master. A dependency bump has not fixed it.

Uncertainty: I did not find what gives a negative-size rect. With normal element rects, the two rects moved to the same corner always intersect. Reproduction details would help: browser and version (the message wording suggests Firefox), browser zoom level, whether the note is in a split, a popup or quick edit, and whether it happens right after a note switch or a page reload. The durable fix looks like an upstream CKEditor change (return `null` from the positioning function when there is no intersection). A Trilium-side patch of ckeditor5-ui would be a workaround.
