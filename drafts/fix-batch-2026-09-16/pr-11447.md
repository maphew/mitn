## Why

Closes #11447

Tab from the note title goes through the promoted label fields and skips each single-valued promoted relation field. The user must click a relation field to reach it.

Each promoted field gets `tabIndex = 200 + definitionAttr.position` and the note title gets 100. `RelationInput` in `PromotedAttributes.tsx` renders `NoteAutocomplete`, which had no `tabIndex` prop, so its `<input>` kept the default tabindex 0. Sequential focus visits positive tabindex values first, thus the relation field came after the full 100/200+/300 band.

This is a regression from the Preact port (first released in v0.100.0). The legacy `promoted_attributes.ts` set `.prop("tabindex", 200 + definitionAttr.position)` on the one `$input` that labels and relations shared. `RelationValuesInput` (multi-valued relations) already had a workaround for the missing prop: `setAttribute("tabindex")` through the input ref. The single-valued path had none.

## What

- `react/NoteAutocomplete.tsx`: new optional `tabIndex?: number` prop, set on the `<input>`. The attribute is absent when the prop is not given, so the other callers do not change.
- `PromotedAttributes.tsx`: `RelationInput` passes `tabIndex={200 + props.cell.definitionAttr.position}`, the same expression that the label, multi-label and multi-relation fields use.
- `attribute_widgets/relation_values_input.tsx`: the `useEffect`/`setAttribute` workaround is removed. The component passes `tabIndex` to `NoteAutocomplete`.
- Specs: new `react/NoteAutocomplete.spec.tsx` renders the real component and asserts `tabindex="205"` with the prop and no attribute without it. `PromotedAttributes.spec.tsx` asserts `"210"` on the relation input. `relation_values_input.spec.tsx` asserts `"205"` on the DOM input.

## Scope

- The positive-tabindex scheme does not change. Controls in a promoted cell that are not the field (chip remove buttons, the colour picker cells, the open-link button of a url label) stay at tabindex 0, so Tab reaches them after the 100/200+/300 band. The durable fix is to remove the scheme and use DOM order. That is a larger change than this regression fix.
- Shift+Tab from the CKEditor body does not leave the editor. This was the same before the fix.
- Definitions from a template can have the same position as the definitions of the note, which gives equal tabindex values. The browser then uses DOM order, which is the render order of the cells.
- Open PR 8972 touches the same files and has no tabindex change. Only a textual conflict is possible.
- No i18n change. No user guide page describes the tab order of promoted attributes, so there is no docs change.
