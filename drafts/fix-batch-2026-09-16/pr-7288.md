## Why

Closes #7288

When you move several notes into a note that has no children, a ghost node can stay under the old parent. The console then shows "Not existing branch '...'". The defect depends on timing, so it does not occur on each attempt.

Root cause: `moveToParentNote()` sends one PUT for each note and waits only for the HTTP response. The first move makes the target a folder, and that starts `froca.loadSubTree()` for the target. The response can list children whose websocket entity changes the client has not processed yet. For each such note, `froca.addResp()` removes the old branch from `froca.branches` and makes no `LoadResults` entry.

When the `isDeleted` change for that branch arrives, `processBranchChange()` called `loadResults.addBranch()` only inside `if (branch)`. The branch is already gone, so the row never gets to `NoteTreeWidget.#processBranchRows()`, which is the only code that removes the node. The same event contains the new branch, so `updateNode()` runs on the stale node and `froca.getBranch()` logs the error.

The log dumps that itsjakobx posted on the issue showed that each ghost is the branch moved immediately before a `GET tree?subTreeNoteId=` request for the target. That evidence pointed to this race.

## What

- `apps/client/src/services/froca_updater.ts`: `processBranchChange()` now registers a deleted branch in `LoadResults` whether or not froca holds it. The path for a branch that is not deleted already did this. The source change is 6 lines added and 4 removed.
- The froca unlink stays inside `if (branch)`.
- The call requires `ec.entity`, because `getBranchRows()` can make a row only from the entity payload. An erased change without a payload continues to cause no event.
- `note_tree.ts` has no change. `#processBranchRows()` finds nodes by `branchId` and does not need froca.
- `froca_updater.spec.ts`: one new spec, one added assertion, and one spec renamed to agree with its assertions.

## Scope

- Behavior change: a batch that contains only deletions of branches that froca does not hold now causes an `entitiesReloaded` event. Before, it caused none. Bulk subtree deletion and sync can make such batches. The result is more refresh work in the widgets, not incorrect state: all `getBranchRows()` consumers filter on `noteId` or `parentNoteId`, and none calls `froca.getBranch()` on a deleted row.
- Not changed: `branches.ts` could call `ws.waitForMaxKnownEntityChangeId()` between moves. That makes the race less frequent but does not repair the dropped delete event.
- Not changed: a stale `loadSubTree` response can arrive after a newer websocket event, and `addResp()` then makes older state again. That is a different race and occurs less frequently.
- Known limit: an erased change without a payload for a branch that froca does not hold continues to supply no row. The `isDeleted` change always comes before the erase, so the delete event removes the node first.
