## Why

On a shared page, a reference link to a note that has `#shareAlias` shows as plain text. The link is not clickable. The same link works in the app. #9596 reports the same defect.

Root cause: in `renderText()` (`apps/server/src/share/content_renderer.ts`), `handleAttachmentLink()` finds the target note from the stored `#root/.../<noteId>` href and then rewrites the attribute to `./<shareId>`. After that, `cleanUpReferenceLinks()` read the rewritten attribute, took the last path segment as a note ID and called `getNote()`. `SNote.shareId` returns the alias when `#shareAlias` is set, and `shaca.getNote()` looks up by note ID only. Thus `./linux` found no note and the anchor was replaced by a text node.

The same defect occurs for a target with `#shareExternalLink` (the last segment of the external URL is not a note ID) and for the share root (`shareId` is empty). The link only worked while `shareId` was equal to `noteId`. This is a regression from 1ceedf2372, first released in v0.100.0. That agrees with the report: good in 0.63.7, bad in 0.102.0.

Closes #8942

## What

- `renderText()` passes the href as stored in the note to `cleanUpReferenceLinks()`, which no longer reads the rewritten attribute.
- New helper `getNoteIdFromLink(href)` removes the query string and returns the last path segment. `handleAttachmentLink()` and `cleanUpReferenceLinks()` both use it.
- `handleAttachmentLink()` removes the `href` of a link whose note or attachment is missing. `cleanUpReferenceLinks()` checks `linkEl.hasAttribute("href")`, so such a link is still replaced by its text and does not become a link to the note that owns the attachment.
- Two specs in `content_renderer.spec.ts`, in `describe("Reference links")`. The diff is +60/-7 in two files.

## Scope

- No alias fallback in `shaca.getNote()`. `share/routes.ts` already resolves aliases with `shaca.aliasToNote`, and a change to `getNote()` would change the lookup for all callers.
- `./${shareId}` is written into the href without percent-encoding, here and in `renderIndex()`. An alias that contains `#`, `?` or `%` still gives a broken link. This is pre-existing and not changed here. It can be a separate issue.
- One small behavior change: a reference link with an external href (not `#...`) now has its query string removed before the note lookup, so `https://example.com/page?x=1` looks up `page` and not `page?x=1`. Before this change, a URL without a query string already had the same lookup. An effect needs a note ID that is equal to the last URL segment, so I made no change for it.
- Remaining uncertainty: issue 8942 writes the link as `[[linux]]`, which is not exact. #9596 names an internal link to a note with `#shareAlias` that shows as plain text, which agrees with this code path. I did not reproduce the defect in a running instance.
