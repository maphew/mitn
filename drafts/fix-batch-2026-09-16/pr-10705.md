## Why

Part of #10705 (this fixes one of the defects listed there and does not close the issue).

A right-click on a launcher icon or on the Web clip badge opens the context menu, but the tooltip of that icon stays on screen and covers the menu items. This is the "Side panel" and "Web Clipper Note" part of the issue. I reproduced it on main with the "New Note" and "Calendar" launchers.

Root cause: `ContextMenu.show()` calls only `note_tooltip.dismissAllTooltips()`, and that function disposes only the note-preview tooltips in `openTooltipElements`. Nothing hides the ordinary Bootstrap tooltips from `useStaticTooltip` (`ActionButton`, `Badge`), `useTooltip` (`Dropdown`, so the Calendar launcher), `tab_row.ts` and `quick_search.ts`. `useStaticTooltip` dismisses on `click` only, and a right-click also focuses the trigger, so the Bootstrap focus trigger keeps the tooltip up. The legacy `abstract_button.ts` hid its tooltip in its `contextmenu` handler. The Preact launchers in `launch_bar_widgets.tsx` do not.

## What

- `apps/client/src/menus/context_menu.ts`: `show()` calls the new `hideShownTooltips()` directly after `note_tooltip.dismissAllTooltips()`. The helper loops over `document.querySelectorAll("[aria-describedby]")` and calls `Tooltip.getInstance(trigger)?.hide()`. Bootstrap sets `aria-describedby` on a trigger while its tooltip is shown, and `hide()` also resets the hover and focus triggers.
- The sweep is in the menu, so it applies to each tooltip creator and each menu entry point. It does not remove elements by the `.tooltip` class, so popups that are not Bootstrap tooltips stay.
- `apps/client/src/menus/context_menu.spec.ts`: one new test. It shows a tooltip with `.show()` and again through `focusin` (the right-click state), and after each `contextMenu.show()` the `.tooltip` element and `aria-describedby` must be gone. A field with its own `aria-describedby` and no tooltip must keep the attribute.

## Scope

- Issue 10705 lists more than one defect. This PR fixes only the launcher and badge tooltip over the context menu. These stay open and need their own changes: the tooltip that comes back when a dialog closes and focus returns to the launcher, the PDF menus that do not close on a click in the PDF, the context menu behind the prompt modal, and menus longer than the viewport.
- The sweep runs one time, when the menu opens. A tooltip that Bootstrap shows after that can still cover the menu. Two examples: the pointer goes off the launcher and back while the menu is up, or a right-click on a tab comes before the 500 ms show delay of the tab row tooltips ends. The two reviews found this gap independently. It is not new with this change. A `show.bs.tooltip` guard while `body.context-menu-shown` is set can close that gap. I left it out to keep this change small.
- Known side effect: the quick search error tooltip (`quick_search.ts`, manual trigger, 4 seconds) now hides early if a context menu opens in that time.
- `Tooltip.getInstance()` returns null for a tooltip on an element that a different Bootstrap component owns (see the comment in `useTooltip`). No tooltip creator in the client does that today, because `Dropdown` binds its tooltip to the wrapper and not to the toggle.
- The fix relies on the event order mousedown, focus, then `contextmenu`. I verified this order only in Chromium on Linux. A check on macOS is welcome.
